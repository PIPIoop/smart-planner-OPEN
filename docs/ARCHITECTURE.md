# Архитектура Smart Planner

## Общая схема

```text
Flutter Presentation → PlannerViewModel → TaskRepository ─┐
                                                          ├→ FastAPI → SQLite
Telegram → Whisper → TaskExtractor → TaskApiClient ───────┘
```

`PlannerTask`, `PlannerGoal` и JSON API образуют общий контракт. Flutter и Telegram не зависят от внутреннего кода друг друга.

## Flutter

- `domain` — `PlannerTask`, `PlannerGoal`, черновики, календарные сущности, расчёт расписания и прогресса;
- `application` — `PlannerViewModel`, пользовательские сценарии и состояние;
- `data` — интерфейс `TaskRepository`, локальная и HTTP-реализации;
- `presentation` — адаптивная страница, диалоги и шестишаговое обучение.

ViewModel обновляет память только после успешного ответа репозитория. В API-режиме `PlannerBootstrap` раз в 2 секунды вызывает `synchronize()`: изменившийся серверный список применяется без перезагрузки Flutter-страницы. Счётчик ревизии защищает локальные записи от запоздавшего фонового ответа. Создание, изменение и удаление используют отдельные атомарные методы. `replaceAll` применяется для явного импорта и полной очистки.

## Task API

- `models.py` — строгий Pydantic-контракт с именами полей Dart;
- `service.py` — ID, UTC-метки и идемпотентное создание;
- `repository.py` — параметризованный SQLite CRUD и транзакции;
- `app.py` — FastAPI endpoints и локальный CORS;
- `config.py` — путь БД, host и port из окружения.

Приложение FastAPI создаётся фабрикой. Поэтому импорт модуля в тестах не создаёт рабочую БД как побочный эффект.

## Telegram

- `transcriber.py` — распознавание OGG через faster-whisper;
- `task_extractor.py` — детерминированный разбор русского текста;
- `confirmation_store.py` — временные подтверждения, привязанные к user/chat;
- `task_api_client.py` — преобразование результата в общий контракт и POST;
- `bot.py` — Telegram handlers и управление потоком.

## Режим совместимости

Локальный Flutter-режим сохранён для автономной работы. Он не синхронизируется с API автоматически. Общий режим включается только через `TASK_API_URL`; это позволяет постепенно мигрировать существующие данные через JSON экспорт/импорт.
## Цели и прогресс

Создание цели — одна атомарная операция репозитория: вместе сохраняются `PlannerGoal` и все задачи её расписания. `endDate` обязательна, повторения включают начальную дату и идут с шагом `intervalDays`, максимум 1000. У задачи хранятся `goalId` и неизменяемая `goalOccurrenceDate`; поэтому задачу можно перенести, а удаление не уменьшает ожидаемое число повторений.

Прогресс вычисляется из расписания цели, а не из количества оставшихся задач. Выполнение вовремя имеет вес 1, позднее — 0,6. Смайлик определяется сочетанием доли выполненных повторений и своевременности: своевременное движение делает его веселее, пропуски и опоздания — грустнее. `completedAt` сохраняет фактический момент выполнения; миграция старой SQLite-базы заполняет его прежним `updatedAt`.

## Группы и Telegram-отчёты

`TaskGroup` — отдельная сущность с `id`, названием и уникальным `colorHex`. `PlannerTask.groupId` необязателен: одна задача относится максимум к одной группе. Flutter синхронизирует группы тем же фоновым циклом, что задачи и цели. Удаление группы выполняется транзакционно: сама группа удаляется, а связанные задачи остаются и получают `groupId = null`.

Палитра содержит 12 приятных цветов. Уникальность обеспечивается одновременно в ViewModel, локальном репозитории и SQLite UNIQUE-индексом.

Telegram-команда `/report` запрашивает задачи и группы через `TaskApiClient`. `report_renderer.py` вычисляет границы текущей недели (понедельник–воскресенье) или календарного месяца, считает выполнение вовремя/позже/пропуски и формирует HTML-caption плюс PNG 1200×820. Бот не читает SQLite напрямую.

## Детерминированный Telegram-секретарь

`secretary.py` — чистый слой анализа календаря: границы дня/недели, пересечения интервалов, свободные окна и умеренные рекомендации. Рабочее окно сейчас 09:00–18:00, резерв между задачами — 15 минут, длительность новой задачи со временем по умолчанию — 60 минут. Задачи на весь день и выполненные задачи не создают временных конфликтов.

`bot.py` отвечает только за меню и сценарии подтверждения, а `TaskApiClient` — за общий REST-контракт. Все мутации проходят цепочку «предпросмотр → подтверждение → PUT/DELETE/POST». Ранний owner guard сравнивает Telegram user ID с обязательным `TELEGRAM_OWNER_USER_ID` и останавливает обновление до любого другого обработчика. Проактивные фоновые рассылки пока намеренно отсутствуют.
## Multi-tenant boundary

Реестр `users.sqlite3` хранит только профиль, роль и статус. `tasks.sqlite3` остаётся базой администратора для обратной совместимости, а каждый обычный пользователь получает отдельную хешированную SQLite-базу в `data/tenants`. Выбор репозитория выполняется сервером только после проверки HMAC-пользователя или краткоживущей admin web session. Подробности и эксплуатационные сценарии описаны в `MULTI_USER.md`.
